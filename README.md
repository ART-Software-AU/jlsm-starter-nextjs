# JSON-LD Schema Manager — Next.js add-on

Adds the JSON-LD Schema Manager renderer to a Next.js head built on the Sitecore Content SDK, App Router or
Pages Router.

JSON-LD Schema Manager (JLSM) compiles each graph onto the datasource of a `JSON-LD` rendering and places that
rendering on pages through a partial design, in the `jlsm-jsonld` placeholder. Your head renders that
placeholder; the first `JSON-LD` rendering on the page writes one `<script type="application/ld+json">`
holding every graph on the page, in the **body**.

These instructions are written for the Next.js examples in Sitecore's
[`sitecore-xmcloud-starter-js`](https://github.com/Sitecore/sitecore-xmcloud-starter-js) repository:
`examples/basic-nextjs` (App Router), `examples/basic-nextjs-pages-router` (Pages Router) and the
`kit-nextjs-*` kits. A head made with `create-content-sdk-app` has the same layout and component map.

It is a drop-in, not a package: you copy three files into your head and own them from there.

## What is in this repository

| Path | Holds |
|---|---|
| `src/lib/jsonld/jsonld.ts` | The engine |
| `src/lib/jsonld/JsonLdScript.tsx` | The React component that writes the script |
| `app-router/src/components/json-ld/JSON-LD.tsx` | The `JSON-LD` component for the App Router |
| `pages-router/src/components/json-ld/JSON-LD.tsx` | The `JSON-LD` component for the Pages Router |

## 1. Add the placeholder to `Layout.tsx`

Render a placeholder with the key `jlsm-jsonld` in `src/Layout.tsx`, before the header. The key is set in
JLSM Settings on the dashboard; if you change it there, use the same key here.

**App Router** (`examples/basic-nextjs`):

```tsx
<>
  {route && (
    <AppPlaceholder
      page={page}
      componentMap={componentMap}
      name="jlsm-jsonld"
      rendering={route}
    />
  )}

  <header>…</header>
  <main>…</main>
  <footer>…</footer>
</>
```

**Pages Router** (`examples/basic-nextjs-pages-router`):

```tsx
<>
  {route && <Placeholder name="jlsm-jsonld" rendering={route} />}

  <header>…</header>
  <main>…</main>
  <footer>…</footer>
</>
```

In both, the placeholder goes in the fragment that renders the header, main and footer, not in the
`mode.isDesignLibrary` branch. Placed first, the script is near the top of the HTML, and in the Pages editor
the `{ } JSON-LD` chip shows above the header, where authors see it.

## 2. Copy the component into your project

| Copy from this repository | To your head |
|---|---|
| `src/lib/jsonld/jsonld.ts` | `src/lib/jsonld/jsonld.ts` |
| `src/lib/jsonld/JsonLdScript.tsx` | `src/lib/jsonld/JsonLdScript.tsx` |
| `app-router/src/components/json-ld/JSON-LD.tsx` **or** `pages-router/src/components/json-ld/JSON-LD.tsx` | `src/components/json-ld/JSON-LD.tsx` |

- Copy the files, do not retype them: `jsonld.ts` holds escape sequences that retyping can corrupt.
- Keep the file name `JSON-LD.tsx`. The component map generator takes the map key from the file name, and
  the key must be `JSON-LD`.
- Keep the engine in `src/lib`, outside `src/components`, so the generator does not register it as a
  component.
- The components import the engine as `lib/jsonld/…`, the alias the starter's `tsconfig.json` already
  declares.

## 3. Register the component in `.sitecore/component-map.ts`

The starter generates `.sitecore/component-map.ts` from `src/components` on every `npm run dev` and
`npm run build` (`sitecore-tools project component generate-map`). With `JSON-LD.tsx` copied, the next run
adds the entry for you. The file then holds:

```ts
// .sitecore/component-map.ts (generated by sitecore-tools project component generate-map)

// … built-in components and your other imports
import * as JSONLD from 'src/components/json-ld/JSON-LD';

export const componentMap = new Map<string, NextjsContentSdkComponent>([
  // … built-in components and your other components
  ['JSON-LD', { ...JSONLD }],
]);

export default componentMap;
```

If your head maintains the map by hand (its `dev` and `build` scripts do not run `generate-map`), add the
import and the `['JSON-LD', { ...JSONLD }]` entry yourself.

- The key is `JSON-LD`, the rendering's component name in Sitecore.
- In the App Router the component is a server component, so it belongs in `component-map.ts` only. It does
  not go in `component-map.client.ts`.
- JLSM delivers each graph inside a partial design, so the map also needs `PartialDesignDynamicPlaceholder`.
  The starters include it.

## 4. The rendering in Sitecore

JLSM's Plugin Setup already creates and registers everything Sitecore needs. There is nothing to add by hand:

| Item | Path |
|---|---|
| The `JSON-LD` rendering (Json Rendering, component name `JSON-LD`) | `/sitecore/layout/Renderings/Feature/JSON-LD/JSON-LD` |
| The placeholder settings for `jlsm-jsonld`, allowing only the `JSON-LD` rendering | `/sitecore/layout/Placeholder Settings/Feature/JSON-LD/JSON-LD` |
| `jlsm-jsonld` in the Headless Layout's Layout Service Placeholders, so every page returns it | `/sitecore/layout/Layouts/Foundation/JSS Experience Accelerator/Presentation/JSS Layout` |

Publish the layout and the placeholder settings folder after Plugin Setup runs. On a tenant without the
Headless Layout, Plugin Setup asks you to add `jlsm-jsonld` to your own layout's placeholders.

> **Do not rename the rendering or change its Component Name.** The head finds JSON-LD renderings by the
> name `JSON-LD`: it is the component map key, and the engine walks the layout for components of that name.
> Under any other name the rendering maps to nothing and the page emits no JSON-LD.

## How it renders

- Every `JSON-LD` rendering on the page renders the component. The first one in the layout writes the script
  for all of them, with entities shared between graphs written once; the rest render nothing.
- **App Router:** the component is an async server component. It reads the page's dates itself.
- **Pages Router:** the component exports `getComponentServerProps`, so the dates are read in the page's
  `getStaticProps` or `getServerSideProps` (the starter's `client.getComponentData` runs it), and the
  component reads them with `useComponentProps`.

### Page dates

The page's created and updated dates are the one thing the layout does not carry, so `readPageDates` reads
them from Experience Edge with `SITECORE_EDGE_CONTEXT_ID`, the context id the head already has. It asks only
when a graph on the page uses a date, holds the answer five minutes, and gives `null` after a failure or two
seconds, in which case the page still emits without `datePublished` and `dateModified`. Both components read
on the server, so the context id does not reach the browser.

We're working on a mechanism to avoid this round-trip in an upcoming version. Today, the extra round-trip
is only executed if your schema includes the `♣page:created` or `♣page:updated` tokens. We advise avoiding use
of the `♣page:created` token in particular for the time being.

### Editing mode

In the Pages editor the component emits no script and shows an inline `{ } JSON-LD` chip with the size of
what the published page carries. Its outer element has `class="jsonld-marker"`.

### Contract

This renderer reads contract **2**: the datasource carries `jsonTemplate`, `references`, `jlsmSiteRoot`,
`jlsmDefaultLanguage` and `jlsmContract`. A datasource on another contract emits nothing. Upgrade the app,
republish every graph, then copy the new files here.

## Checking it

On a published page, view the source: there should be exactly one `application/ld+json` script, in the body,
with `data-source` naming JSON-LD Schema Manager, and its `@graph` should hold one node per entity.
